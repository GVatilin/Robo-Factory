# Датасеты

Крупные исходные файлы и скачанные изображения в git не хранятся. В репозиторий входят скрипты загрузки, справочные JSON-манифесты со ссылками на источники и инструкции.

## Какие файлы положить

| Файл | Что это | Как скрипт его находит |
|---|---|---|
| `catalog_export_v4.csv` | Каталог решений организатора | Самый свежий `catalog_export*.csv` по имени |
| `Датасеты_хакатон.xlsx` | Демо-параметры склада, аэропорта и медучреждения | Любой `.xlsx` с листами «Склад», «Аэропорт», «Медучреждение» |
| `reference_specs.json` | ТТХ эталонных решений из «Примеры_решений_типы_объектов.docx» с источниками | Точное имя |
| `Примеры_решений_типы_объектов.docx` | Фото и ТТХ эталонных решений | Самый свежий `Примеры_решений*.docx` по имени |

Если файла нет, соответствующий шаг пропускается.

## Как загрузить

Backend должен быть запущен: при старте он создаёт базовые справочники, от которых зависят датасеты.

```bash
docker compose up -d
docker compose exec backend python /datasets/load_datasets.py
```

Папка `datasets/` смонтирована в контейнер backend как `/datasets` только для чтения.

Скрипт выполняет все шаги в одной транзакции: при ошибке в данных ничего не сохраняется. Повторный запуск безопасен. Файл с той же контрольной суммой пропускается, а новая версия обновляет данные и записывается в `dataset_versions`.

Другие пути к файлам:

```bash
docker compose exec backend python /datasets/load_datasets.py \
  --catalog /datasets/catalog_export_v5.csv --facilities /datasets/other.xlsx --photos /datasets/examples.docx
```

Запуск с хоста без Docker. Нужны зависимости из `backend/requirements.txt` и доступ к БД:

```bash
export DATABASE_URL=postgresql+asyncpg://robo:robo@localhost:5433/robofactory
python datasets/load_datasets.py
```

## Что загружается

1. **Каталог:** продукты, производители, применения по отраслям с кейсами, цены как предложения.
2. **Параметры объектов:** описания параметров с единицами, диапазонами, значениями по умолчанию и источником.
3. **Эталонные ТТХ:** значения характеристик с источником и датой. Продукты, которых нет в каталоге, добавляются.
4. **Фото и ТТХ решений.** Строки ТТХ под подписью («Грузоподъёмность: до 1500 кг.») переводятся в единицы справочника: тонны в кг, км/ч в м/с, см в мм, минуты в часы. Для характеристики-числа из диапазона берётся верхняя граница («около 2000–2500 кг» → 2500 кг). Исходная строка сохраняется в примечании значения. Строки без подходящей характеристики (мощность, топливный бак, вместимость в европаллетах) попадают в отчёт. Если у товара в каталоге указана только категория, тип уточняется по подписи документа («FMR (мобильный вилочный робот)» → FMR). Значения, внесённые в карточку вручную, импорт не меняет.
   **Фотографии:** фото из таблиц документа привязываются к карточкам по модели из подписи «(на примере модели …)». Растр из EMF, в который Word упаковывает фото, извлекается без внешних программ. Решение, которого нет в каталоге (PuduBot 2), добавляется карточкой. Фото, загруженное в карточку вручную, импорт не заменяет.
5. **Демо-проекты:** по одному на тип объекта, с тремя сценариями.

Логика разбора файлов находится в `backend/app/services/`. Её же будут использовать админские роуты загрузки.

## Иллюстрации решений из открытых источников

`catalog_illustrations.json` сопоставляет типы решений с изображениями Wikimedia Commons.
Для каждого скачивания сохраняются автор, лицензия, ссылка на оригинал, дата и SHA-256.
Картинки хранятся локально, внешние ссылки не используются для показа в каталоге.

```bash
python datasets/fetch_catalog_illustrations.py
docker compose up --build -d
docker compose exec -T backend python /datasets/load_catalog_illustrations.py
docker compose exec -T backend python /datasets/load_catalog_illustrations.py --apply
```

Без `--apply` выводится план импорта. Существующие изображения сохраняются;
повторный запуск заполняет только карточки без картинок. Скачанные файлы находятся
в игнорируемой папке `datasets/illustrations/`, после импорта — в Docker volume `uploads`.
Иллюстрации обозначены в каталоге, сравнении и карточке решения: это похожий тип
оборудования, а не подтверждённое фото конкретной модели. Источник и лицензия
доступны в карточке. Реальное фото из документа может заменить иллюстрацию.

## Параметры отдельных проектов

ТЗ, раздел 3.2.1: каждому типу объекта соответствует своя схема параметров.
В текущем загруженном датасете: склад — 45 полей (25 обязательных), аэропорт —
46 (23 обязательных), медучреждение — 58 (22 обязательных). Дополнения по ТЗ
добавляются при запуске backend; пользовательские проекты сохраняют свои значения.

`parameter_definitions` содержит определения с ключом `(facility_type_id, code)`.
Каждая строка `projects` хранит собственные `parameters` и `parameter_origins` в JSONB
и ссылку `facility_type_id`. Поэтому два склада имеют одинаковые определения полей,
но независимые значения. Сервер проверяет ручной ввод и CSV/XLSX по схеме выбранного
типа и отвергает посторонние ключи. Форма получает определения через
`/projects/parameters/{facility_type_id}` и показывает обязательные и дополнительные поля.

Подробности раздела 3.2, шаблонов и расширения справочников: [docs/object-inputs.md](../docs/object-inputs.md).

## Фотографии моделей и подтверждённые характеристики (п. 3.3.4)

`catalog_evidence.json` сопоставляет 187 позиций с изображениями и страницами
предоставленного PDF ФЦ БАС. `official_enrichment.json` содержит 141 характеристику
14 моделей с официальных сайтов Ronavi, МОРОС, R2B, Клинботикс, Геоскан, ГНОМ и Pudu.
Дата чтения официальных страниц — 29.09.2026. Это подтверждение публикацией
производителя, а не независимая проверка заявленных возможностей.

```powershell
python datasets/prepare_catalog_evidence.py --pdf "C:\Users\fan1g\Downloads\ФЦ БАС — Каталог внедрения 2008 1247.pdf"
docker compose exec -T backend python /datasets/load_catalog_evidence.py --apply
```

Для извлечения изображений на хосте нужен PyMuPDF. Должны быть доступны исходные
CSV и DOCX в `datasets/`. Полученные изображения и PDF находятся в игнорируемой
папке `datasets/evidence/`; после импорта документы и нормализованные изображения
хранятся в постоянном Docker volume `uploads`. В репозиторий входят манифесты,
ссылки и контрольные суммы, сами крупные исходные документы — нет.

Импортёр проверяет контрольные суммы и точное сочетание названия изделия и
производителя. Заменяются только иллюстрации; ручные фотографии и характеристики
с посторонними источниками сохраняются. Предыдущие значения организатора остаются
в `products.source_payload.enrichment_history`. Повторный импорт не создаёт дубликатов.

У каждой ТТХ показаны источник, дата, подтверждение и условия измерения. После
дополнения и разбора расхождений 14 противоречивых характеристик помечены «Требует уточнения» и не имеют числового
значения для расчётов. Соответствие изображения 85ТК модификации 85.0ТК также
не подтверждено и явно обозначено. Для остальных моделей недостающие официальные
ТТХ требуют дальнейшего поиска или запроса производителю; пустые поля не заполняются
оценками. Цены организатора не превращаются в подтверждённые коммерческие предложения.

Отчёт загрузки: `/data/uploads/catalog-enrichment-report.json` в backend-контейнере.
Маршрут `/api/v1/catalog-documents/{document_name}` отдаёт только три разрешённых
документа: каталог PDF, исходный CSV и документ с примерами решений.
